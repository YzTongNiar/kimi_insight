为什么 P 的 Attention/MoE 饼图没有通信主导算子？
P 阶段的 68.7% 来自整个阶段的 step_trace_time.csv，包含所有 HCCL、all-gather、reduce-scatter、broadcast、send/receive 等通信；Attention/MoE 饼图只统计 Attention 和 MoE 计算算子，独立的通信算子被归入 Other，因此两者统计范围不同。P 的通信主要来自跨卡通信路径，并不意味着每个 Attention/MoE kernel 内部都由通信主导。另一个差异是：68.7% 是 Stage 墙钟时间线的通信占比，饼图是 Attention/MoE 算子累计时间构成，不能直接互相替代。
通信算子统计口径修正：MindStudio Insight Communication View 中的 hcom_alltoallv_ 来自 kernel_details.csv 的通信 kernel 类型；此前 Attention/MoE 全量饼图主要使用 op_statistic.csv，该文件不包含 hcom 通信 kernel，所以漏掉了 all-to-all。P 的通信 kernel 类型中，hcom_broadcast_ 约占 kernel 累计时长 28.27%，hcom_alltoallv_ 约占 16.63%，hcom_send_ 约占 5.15%，hcom_reduceScatter_ 约占 4.71%，hcom_allGather_ 约占 4.15%。MindStudio 显示的 19.75% 与这里的具体数值可能不同，因为它使用的分母和时间去重规则不同；但 all-to-all 确实应从 Communication View 统计，而不是从 op_statistic.csv 推断。

3. 算子瓶颈与优化优先级

P Attention ChunkKdaFwd → FusedInferAttentionScore优先检查 KDA 的 kernel 融合、KV/中间张量读写、布局转换和 tiling；并将 Attention 计算与通信等待流水重叠。
P MoE GroupedMatmulWeightNz → DequantSituQuant / DynamicQuant → QuantBatchMatmulV3重点优化专家 token 聚合、小矩阵利用率、量化与 matmul 融合，以及 token permute；同时优化 all-to-all/dispatch/combine 与专家计算的重叠。
D Attention FlashMlaWithKvcache → RecurrentKda → AttnResFwdFused优先检查 KV cache 访问合并、cache layout、单 token 向量化、MTE 利用率和 launch/同步固定开销。
D MoE GroupedMatmulSituQuant → GroupedMatmulWeightNz → QuantBatchMatmulV4/V3针对 decode 的小 token batch 选择低延迟 tiling，融合 grouped matmul 与 situ quant，并检查 dispatch/combine 的搬运和专家负载均衡。
